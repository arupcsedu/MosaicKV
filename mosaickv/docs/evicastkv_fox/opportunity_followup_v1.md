# Finite event-driven opportunity follow-up

This controller does not claim that an interactive Codex session wakes itself.
It implements **one explicitly bounded follow-up** with Slurm completion
dependencies. No loop tails logs, reads interim quality, changes source, tunes
coefficients, replaces samples, or keeps sampling until significance.

The first study is the registered 64-input, 20/40-MiB factorial comparison from
`a2adfc3`, array 22123858 and CPU analysis 22123859. It completes all 832
requests before quality is read. The follow-up is registered before those
outcomes are examined. The old 1/256 policy remains immutable.

If any variant has the registered positive development signal against Top-K
and VL-Cache at both budgets, do not launch the fallback. If execution is
incomplete or invalid, block rather than treating that as algorithm failure.
If the complete first study is negative/inconclusive, test **1/16 routed
participation**: the original checkpoint has 256 layer/head routes, so this
increases participation from one to 16. More opportunity-ranked routes can
actually change selection, without changing any cache capacity or precision.
This is a plausible mechanism experiment, **not a guaranteed improvement**.

The sole algorithm-treatment changes are the consistent graph/prototype
configuration route fractions. Templates are copied into new immutable roots;
all model execution uses the unchanged, clean `a2adfc3` source. No prototype
merging is enabled: the historical prototype namespace also contains exact-mode
routing controls. Budgets, scalar coefficients, window 16, shortlist, graph
degree, mandatory policy, original K/V, per-query 0.95 floor and append schedule
are unchanged. Retention-one identity is still mandatory.

The r16 factorial comparator uses **entropy at r16**, not the original frozen
entropy-r256 comparator. Label that distinction in every interpretation; do not
pool its `complete` rows with r256. All four r16 policy arms share the same
routed count. Top-K and `vl_cache_reimpl` still use their unchanged controls at
both shared budgets. Comparisons are within a protocol, not between unrelated
isolated points.

First run a 26-request, two-consumed-input independent-representation canary.
Only its clean numerical/storage pass can release the **same original 64
consumed development identities** at r16, with 832 requests and the same 18
registered exploratory contrasts. Preserve all outcomes. The controller stops
after that second study, regardless of its outcome. These two exploratory
families are not independent confirmation and may not support a paper-level
superiority claim by selecting the favorable one.

Resources remain at most six A100s aggregate, one A100/12 CPUs per worker,
`bii-gpu`/`bi_fox_dgx`; 30-minute canary and 90-minute four-input development
shards. CPU callbacks use `afterany` and write-once decisions, so producer
failure is analyzed. GPU and analysis submission IDs are persisted separately
to retain evidence even if a later scheduler submission fails. No other users'
jobs or active source trees are changed.

Maximum additional GPU scope: 26 + 832 requests. No new cohort, no independent
confirmation, no calibration enlargement, no prototype/repair performance and
no automatic paper claim are authorized by this controller. A positive
development signal still needs a frozen configuration, COCO-only freshness
audit and an independently powered prospective validation. A negative result
remains negative rather than weakening the thresholds.
