This is a preregistered **consumed-development diagnostic**, not a fresh
confirmation campaign. EviCastKV and MosaicKV name the same project. The
retention, source and six-mechanism variants remain separately labeled.

The user's explicit six-A100 authorization overrides the older four-GPU
repository default for this registration only. One global array, not separate
six-worker arrays, enforces the aggregate ceiling. Each worker requests one
A100, twelve CPUs, 64 GiB host memory and at most two hours, in `bii-gpu` under
`bi_fox_dgx`. Existing own GPU allocations/pending arrays are completion
dependencies; other users' jobs are never modified. Entry checks refuse model
work if aggregate own GPU occupancy exceeds six. CPU work uses `bii`.

## Finite execution

`evicastkv_review_parallel.py register` is dry-run by default. With `--execute`
it binds the clean source, passed parent gates and previous final report,
submits the complete CPU suite, and then prepares each independent lane. A
failed preparation is retained and does not masquerade as a submitted worker.
One `%6` GPU array contains all ready tasks; a CPU `afterany` analysis handles
both successful and failed producers. A separate bounded CPU metadata audit
runs independently. There is no continuous log-polling loop or duplicate retry.

No code here authorizes best-seed selection, benchmark-answer tuning, changing
tolerances, freezing a winner, prototype/repair claims, or fresh confirmation.
After diagnostic results, unresolved empirical failures require a separately
versioned correction; extra samples cannot certify a failed numerical control.
Prompt-length scaling, a validated GQA source adapter and a genuine common-byte
source/retention bridge remain distinct requirements if those claims are kept.

All caches and temporary files use the scratch cache environment; the pinned
common Python environment and installed packages are unchanged. An immutable
registration and job ledgers, not this planned table, record actual submissions.
